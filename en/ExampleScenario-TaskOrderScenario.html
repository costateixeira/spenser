ExampleScenario: Scenario - Ordering through an order server (Experimental)

Official URL: http://costateixeira.github.io/spenser/ExampleScenario/TaskOrderScenario Version: 1.0.0
Active as of 2026-11-13 Computable Name: TaskOrderScenario

A placer puts an order and a Task on an order server. The unit polls the server, dispenses what is addressed to it, and reports back what it did.

Actors

NameTypeDescription
Order Placer System

Creates the order and the Task, and closes the order once the Task is done. A Task closes itself; a MedicationRequest does not.

Order Server System

A plain FHIR server. It holds the order and the Task until a unit collects them, and it has to answer _include=Task:focus.

Spenser Unit System

Acting here as a FHIR client. It takes only the work addressed to it and leaves everything else alone.

Diagram

Processes

Process: Order a chocolate through an order server

Place the work, let the unit find it, and read back what it did.

Pre-conditions:

The unit has been pointed at the order server and its polling is on. The unit has written its own Device on the server, so a Task can name it.

Post-conditions:

A chocolate has been dispensed, the dispense is on the server, the Task is completed, and the order is closed.

2 POST /Task - create (Details: FHIR Restful Interactions code create)

code is fulfill, focus is the order, requestedPerformer is the unit. Leave requestedPerformer out and any unit polling that server may take it.

 Order Placer Order Server requested

Alternative Tag the order instead of creating a Task

Put actionable from common-tags in the order's meta.tag and skip the Task. A unit accepts both routes on every check, and orderMode narrows it to one. With no Task coordinating the work the unit completes the MedicationRequest itself, and step 6 does not happen.

3 GET /Task - search-type (Details: FHIR Restful Interactions code search-type)

GET /Task?status=requested&_include=Task:focus&_count=5. The unit polls on a timer, and a check can also be asked for by hand. Each check looks at the first five results only, so a long queue on the server can outrun one check. The unit remembers what it has already dealt with.

 Spenser Unit Order Server requested
4 POST /MedicationDispense - create (Details: FHIR Restful Interactions code create)

The servo turns and a piece drops out, and then the unit says so. The write is queued and retried, so a server that was briefly unreachable does not cost the record.

 Spenser Unit Order Server The dispense

Alternative The lane is empty

The unit writes a dispense with status of declined and notPerformedReason.concept of outofstock. Whether the Task is then left open, so a refill retries it, or closed as failed, is the unit's keepOrders setting.

5 PUT /Task - update (Details: FHIR Restful Interactions code update)

PUT /Task/\<id>: status becomes completed, with the dispense in Task.output. Sent with If-Match, so a Task somebody else has moved on is not overwritten.

 Spenser Unit Order Server completed
6 PUT /MedicationRequest - update (Details: FHIR Restful Interactions code update)

PUT /MedicationRequest/\<id>. The placer closes its own order. The unit does not: it was asked to fill one Task, and it has no way of knowing whether the order authorized more than that.

 Order Placer Order Server completed
